# ADR 0001：KIE Gemini 使用流式传输并对 524 限次重试

- 状态：已接受
- 日期：2026-10-23

## 背景

主站的视频分析默认调用 KIE Gemini 3.8 Flash。该通道会把上游错误包装在 HTTP 200 的 JSON 响应中。线上出现 `code: 524`、`msg: "2 times retry fail"`，说明 KIE 在等待上游完整响应时发生网关超时。现有实现使用 `stream: false`，连接在模型生成完成前没有增量数据，并通过 Axios 的 Node HTTP 适配器发送请求。

KIE 官方接口支持 SSE 流式响应。Vercel 分析路由的最长执行时间为 300 秒，修复必须在该预算内完成，也需要限制额外调用带来的成本。

## 决策

1. KIE Gemini 请求统一使用 `stream: true`，服务端消费完整 SSE 并合并文本后再返回现有分析结果，前端接口保持不变。
2. KIE 通道改用原生 `fetch`，避免 Axios `follow-redirects` 的 `url.parse()` 弃用警告。
3. 仅当 KIE 明确返回 524 时重试一次；其他鉴权、额度和输入错误不重试。
4. 两次尝试共享 270 秒总预算，单次最多 180 秒，并在重试前保留至少 30 秒执行预算。
5. 不自动降级到其他模型，确保用户选择、输出质量和计费模型保持一致。

## 备选方案

### 保持非流式请求，只增加重试

上游仍可能在每次尝试中触发相同网关超时，并延长用户等待时间，因此未采用。

### 524 后自动降级到 Gemini 3.5

可提高成功率，但会改变模型输出与成本语义。当前缺少明确的产品授权，因此未采用。

### 完全不重试，只改善错误提示

不会改善成功率，无法满足线上修复目标，因此未采用。

## 后果

- 长生成会持续产生 SSE 数据，降低 KIE 网关因等待完整响应而超时的概率。
- 单次 524 最多触发一次额外调用，存在有限的额外延迟和潜在成本。
- 服务端仍然聚合完整输出，客户端协议和历史记录结构无需迁移。
- 解析器需要兼容 KIE 的 HTTP 200 业务错误、OpenAI SSE 分片和非流式 JSON 回退。

## 验证计划

1. 单元测试覆盖 SSE 分片合并、空格保留、HTTP 200 业务错误、524 单次重试和 402 不重试。
2. 运行 KIE 相关测试、TypeScript 检查、ESLint 和生产构建。
3. 部署到非生产环境后，用多帧视频执行真实 Gemini 3.8 Flash 分析，确认成功结果与日志中没有重复 524。
4. 生产发布后观察 24 小时的 `analysis.error`、KIE 524 数量、请求耗时和调用成本；若仍有连续 524，再单独评估模型降级策略。
